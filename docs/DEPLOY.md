# Deploying the SariPOS demo

This guide deploys SariPOS as a public demo. It uses three free services plus GitHub, and takes about 30 minutes.

| Piece | Service | What it runs |
|---|---|---|
| Database | [Neon](https://neon.tech) | PostgreSQL 17 |
| API | [Render](https://render.com) | `server/`, from [render.yaml](../render.yaml) |
| Web app | [Vercel](https://vercel.com) | `client/`, with [client/vercel.json](../client/vercel.json) |
| Nightly reset + CI | GitHub Actions | [.github/workflows](../.github/workflows) |

Vercel forwards `/api/*` to Render, so the browser only ever talks to one site. That is what lets the login cookie stay `SameSite=Strict` and first-party. Browsers block cookies from a *different* site (third-party cookies).

## 0. Put the code on `main`

GitHub runs scheduled workflows (the nightly reset) only from the default branch. Merge your work into `main` and push it first.

## 1. Pick the demo logins

The demo logins are **public**: the login page shows them. Pick values that you use nowhere else, for example:

| Name | Example |
|---|---|
| Owner password | `sari-owner-demo` (at least 8 characters) |
| Cashier password | `sari-cashier-demo` |
| Owner PIN | `2468` (4–6 digits) |

## 2. Database: Neon

1. Create a project named `saripos` with Postgres 17. For the region, pick **AWS Asia Pacific (Singapore)**, the closest to the Philippines.
2. Open **Connect** and turn **Connection pooling off**, because migrations need a direct connection. Copy the connection string.
3. If the string ends in `&channel_binding=require`, delete that part. Keep `?sslmode=require`.

This string is a **secret**: it's the key to the database. Never commit it.

## 3. The demo data: GitHub

In your repository, go to **Settings → Secrets and variables → Actions**.

1. Under **Secrets**, add `DEMO_DATABASE_URL`: the Neon string from step 2.
2. Under **Variables**, add these three with your values from step 1:
   - `DEMO_OWNER_PASSWORD`
   - `DEMO_CASHIER_PASSWORD`
   - `DEMO_PIN`
3. Go to **Actions → Reset demo → Run workflow**. It creates the tables and loads the demo store. After that it runs by itself every night at 00:00 Philippine time.

## 4. API: Render

1. Go to **New → Blueprint** and pick this repository. Render reads `render.yaml`.
2. Render asks for two values:
   - `DATABASE_URL`: the same Neon string.
   - `CLIENT_ORIGIN`: your future Vercel address, for example `https://saripos.vercel.app`. You can correct it after step 5.
3. When the deploy finishes, open `https://<your-service>.onrender.com/api/v1/health`. It should show `{"status":"ok","db":"ok"}`.

If Render gave the service another address (the name `saripos-api` was taken), put that address in the `destination` in [client/vercel.json](../client/vercel.json) and push.

`JWT_ACCESS_SECRET` is generated by Render. You never see or type it.

## 5. Web app: Vercel

1. Go to **Add New → Project** and import this repository.
2. Set **Root Directory** to `client`. Vercel detects Vite, so leave the build settings as they are.
3. Add these environment variables:

   | Name | Value |
   |---|---|
   | `VITE_API_URL` | `/api/v1` |
   | `VITE_DEMO_OWNER_PASSWORD` | same as `DEMO_OWNER_PASSWORD` |
   | `VITE_DEMO_CASHIER_PASSWORD` | same as `DEMO_CASHIER_PASSWORD` |
   | `VITE_DEMO_PIN` | same as `DEMO_PIN` |

4. Deploy. If the address isn't the one you gave Render as `CLIENT_ORIGIN`, fix it in Render's **Environment** tab. Render redeploys by itself.

## 6. Check it like a stranger would

1. Open the Vercel address in a private window.
2. Tap **As cashier**, sell something, and pay.
3. Log in **as owner** and check **Reports** (30 days of charts) and **Reports → Audit log**. Open the newest `LOGIN_SUCCESS` entry: its "From IP" should be **your own** address.
   - If every login shows the same address that isn't yours, the proxy count is off. Adjust `TRUST_PROXY` in Render: it's `2` for browser → Vercel → Render.
   - Never set it higher than the real number of proxies: that would let anyone fake their IP and dodge the login limits.
4. Put the address in the README's **Live demo** line.

## Good to know

- **First visit is slow:** Render's free plan sleeps after 15 minutes without visitors, so the first request can take about a minute. Neon also pauses when idle.
- **Nightly reset stops after 60 days of no pushes:** GitHub pauses scheduled workflows when a repository sees no activity for 60 days. Any push, or **Run workflow**, turns it back on.
- **Demo mode:** `DEMO_MODE=true` stops visitors from changing or deactivating users. Otherwise one visitor could lock out everyone else.
- **Using it for a real store:**
  - Set `DEMO_MODE` to `false`.
  - Leave out the `VITE_DEMO_*` variables.
  - Don't run the reset workflow: it **wipes** the database.
  - Turn on Neon's backups (point-in-time restore).
